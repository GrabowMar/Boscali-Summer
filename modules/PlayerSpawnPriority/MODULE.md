# PlayerSpawnPriority — Player spawn priority (`player-spawn-priority`)

> One server-side Harmony prefix: when a human player asks a hangar for an aircraft and the only hangar at that airbase able to spawn it is blocked by an AI aircraft still sitting on the spawn point, the AI aircraft is destroyed so the player's spawn goes through.

## Player-facing behaviour

- Human players are no longer locked out of a hangar by a parked/taxiing AI aircraft on its spawn spot ("Players get hangars first" in the mission prompt, PILOT CAREER group).
- Only as a last resort: if any other hangar at the same airbase can spawn the type, nothing is evicted.
- The player's own wingmen (Wing) are never evicted.
- No page, no settings; host decides (clients need nothing).

## How it works

- [PlayerSpawnPriorityModule](PlayerSpawnPriorityModule.cs): metadata + `PatchTypes = { PlayerSpawnPriorityPatch }`; `Install` only logs. Always in the roster ([Core/BoscaliMod.cs](../../Core/BoscaliMod.cs) `Compose`); battlefield module in [MissionProfile](../../Core/Game/MissionProfile.cs), so the "immersion only" preset turns it off.
- [PlayerSpawnPriorityPatch](PlayerSpawnPriorityPatch.cs): prefix on `Hangar.TrySpawnAircraft(Player, AircraftDefinition, …)`. Proceeds only when: server, hangar not disabled and not `Available`, private `spawnedObject` set, airbase alive, no other hangar on `parentAirbase` `CanSpawnAircraft(definition)`, the definition is in `GetAvailableAircraft()`, `spawnedObject` is an `Aircraft`.
- Decision in pure [SpawnPriorityPolicy](SpawnPriorityPolicy.cs)`.CanEvict(playerRequested, aiOccupied, wingMember, closeToSpawn)`: occupant has no `Player`, is not a Wing member (`WingLink.IsWingMember`), and is within `max(clearDistance, length, width, height)` of `GetSpawnTransform()`.
- Effect: `ServerObjectManager.Destroy(occupant.gameObject)` then `Networkavailable = true`; the original `TrySpawnAircraft` then runs normally (the request already passed `Spawner.AllowedToSpawn` and loadout vetting).
- Exceptions are caught and reported through `PatchGuard.Report("PlayerSpawnPriority.TrySpawnAircraft", …)`.

## Settings, network, patches

- No config, no messages. Server-only (`__instance.IsServer`).
- Fragile Harmony bits: injected private fields `___spawnedObject` and `___clearDistance` and the parameter names `player`, `definition` must match the game's `Hangar.TrySpawnAircraft`; a game rename makes Harmony fail to bind the prefix.

## Tests, sim hooks and pinned names

- `tests/BoscaliSummer.Tests` compiles [SpawnPriorityPolicy.cs](SpawnPriorityPolicy.cs) by path (`PlayerSpawnPriorityTests`); keep it pure, in the module root, in namespace `BoscaliSummer.Modules.PlayerSpawnPriority`.
- PatchProbe names `PlayerSpawnPriorityModule` and `PlayerSpawnPriorityPatch` by full name.
- No sim hooks; `nomod sim ls spawn --mod boscalisummer` only finds an unrelated sea-platform scenario.

## Gotchas

- The evicted AI aircraft is destroyed outright through `ServerObjectManager.Destroy` (no RTB, no landing back into stock).
- `SpawnPriorityPolicy.CanEvict` is called with `player != null`, which is always true at that point (checked at the top); the first argument only matters for the tests.
- Other modules' AI (e.g. Squad ace wings, which `IAircraftTaskExclusion` protects elsewhere) are not exempt here; only Wing members are.
- Files sit in the module root (no Patches/ or Domain/ folders); don't move them — nomodkit compiles the policy by path.
